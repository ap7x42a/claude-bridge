# Claude Bridge

Claude Bridge is a Codex plugin. It runs Claude Code from Codex through the existing Claude Code subscription session, inside a bubblewrap sandbox. Codex may use it only when the operator explicitly asks for Claude. The operator's order to use Claude is the operator's authorization for Claude to correct the work on their behalf. A run that finishes returns a verdict that binds the Codex session; a run that ends in an error records a `blocked` verdict that binds it the same way. Version 0.5.0 replaces the read-only, advisory review of 0.4.7.

## What it does

- `claude_review` is the adversarial review. Claude runs with permissions bypassed and the default tool set, minus `Agent` and `Task`. The repository is mounted read-write. Claude may use the shell and web, may alter the submitted work, and may commit its own corrections with a `bridge-verdict:` message. It is told never to push. Host Git, SSH, `gh` and Codex credentials are masked.
- `claude_task` is delegated write-capable work under the same authority, evidence and verdict contract. Claude runs with permissions bypassed, as in a review, so the mounted evidence, the shell and web are reachable; the bubblewrap sandbox is the boundary. With `resumable: true` it returns a handle for `claude_continue`, valid only in the server process that created it.
- `claude_result` polls a job until it completes, or cancels it with `cancel: true`. Jobs have no time limit.
- `claude_bridge_status` checks the sandboxed Claude binary without a model turn and reports `protection`. `claude_verdict` reads the verdict state, protection, hook integrity and `record_failure` (`present`, `recorded_at`, `message`, from the marker file or the in-process latch) for a repository.

Before each job, the bridge finds the calling Codex session log: the transcript the hook recorded for this bridge call (`match: ledger`, see Session evidence under Enforcement), else the log under `~/.codex/sessions` that holds the prompt. It mounts this evidence for Claude at `/tmp/claude/evidence`: `conversation.md` (the operator's and Codex's messages, each labelled verified or unverified, or a placeholder when no session log was located), `brief.md` (Codex's prompt verbatim, treated as a claim), `bridge-history.md` (earlier calls and verdicts for this repository) and `manifest.json`. A bridge-owned system prompt names these files, grants the authority and requires the verdict schema.

The bridge starts Claude with `--setting-sources ""`, `--strict-mcp-config --mcp-config <bridge config>`, `--disable-slash-commands` and `--no-chrome`. No settings file is loaded, so the host's settings, plugins and hooks stay out, and the bridge supplies an empty strict MCP configuration. Inside the sandbox, for reviews and tasks alike, `PATH` is `/usr/local/bin:/usr/bin:/bin`, and `~/.local/bin` is bound only when the Claude binary itself lives there, which happens only for a checkout run, never for the pinned binary.

Every run, review or task, uses `claude-fable-5-1` (alias `fable`), falling back to `claude-opus-5-5` (alias `opus`) only when Fable is unavailable; a request for `claude-opus-5-5` runs it with no fallback. Codex cannot choose another model: any other `model`, such as `haiku`, `sonnet` or `claude-opus-5`, is refused with `model_not_allowed` before the job starts, and the tool schemas list only the two ids. Effort is `high` at the least: `low` and `medium` run as `high`, and the result then carries `effort_requested` beside `effort`. `claude_continue` keeps the session's model and effort, and refuses a session recorded with a model outside the two.

The model a result reports as selected is the model the bridge asked for whenever Claude reports usage for it, whatever side models it also reports. A configured fallback counts as selected only when the requested model is absent from that usage and the fallback is present.

## Install

Use an ordinary Git clone with its `.git/` directory inside the checkout as the
review target. Linked worktrees and submodules with external Git metadata are
not supported by the sandbox mounts. See the [repository README](../../README.md)
for prerequisites and Codex marketplace registration.

The first install runs from the repository checkout:

```
sudo plugins/claude-bridge/bin/install.sh --claude-bin "$(readlink -f ~/.local/bin/claude)"
```

Upgrades run from the installed copy, naming the checkout to install from:

```
sudo /opt/claude-bridge/current/bin/install.sh --source <checkout>
```

Every install, first or upgrade, must come from a clean checkout: as the owner, `git status --porcelain --ignored -- plugins/claude-bridge` must print nothing and `git ls-files -v -- plugins/claude-bridge` must show no file marked skip-worktree or assume-unchanged; otherwise the install refuses and lists what it found, and a source that is not a readable Git checkout is refused too. The owner's git is run with `--no-replace-objects`, so a `refs/replace` ref or a corrupted object in the owner's checkout cannot make git report a tree the working files do not have; a `sha256` repository is refused. Root builds the new tree in a root-only staging directory (`/opt/claude-bridge/.staging-<version>-<pid>`), scans it for symlinks and any non-regular, non-directory entry before reading it, and checks the copy against the committed tree: it hashes every file it copied under `mcp`, `hooks`, `bin`, `.codex-plugin` and `skills`, and the launch config as read from the source, with its own `git hash-object --no-filters`, and compares them with `git ls-tree -r HEAD:plugins/claude-bridge` read as the owner. A missing, extra or different file refuses, the staged copy is removed and the previous install is left live. `--allow-dirty` installs anyway and records `clean: no`. Only after the staged tree is verified and locked is it swapped into place: `/opt/claude-bridge/current` always points at a verified, locked tree, and a refused install leaves the previous install live. `<version>/INSTALLED-FROM`, root-owned like the rest, records the checkout path (`source:`), the owner-reported `source_commit:` and `source_tree:`, `clean:`, the root-computed subtree ids (`installed_tree_mcp:` and so on for `hooks`, `bin`, `.codex-plugin`, `skills`) and `installed_mcp_json_source:`; the install prints those ids so the owner can compare them against a trusted clone (`git rev-parse <commit>:plugins/claude-bridge/mcp` and the rest). A corrupted or replaced object in the owner's own checkout is not detected by the install, only made visible by those ids. The installed copy refuses to install without `--source`.

It copies the runtime to `/opt/claude-bridge/<version>`, points `/opt/claude-bridge/current` at it, and makes every file root-owned and immutable. The runtime includes a copy of the owner's Claude binary at `claude/claude`, exactly one regular file: `--claude-bin FILE` (a link is refused; pass the file it points to, for example `--claude-bin "$(readlink -f ~/.local/bin/claude)"` when Claude's native installer left a link there), else the first regular non-link file among `~/.local/bin/claude`, `/usr/local/bin/claude` and `/usr/bin/claude`; the installer runs no owner shell, profile or alias to find it. Every check of it runs as the owner and it is read as the owner into a fresh file root creates in the install, which is the only file whose mode root sets; a directory is refused. Whatever ends the install, `/etc/claude-bridge/owner.key` is left at mode 0400. The installed bridge runs only that copy, so a Claude Code update reaches the bridge when the owner reinstalls. It creates the owner key pair in `/etc/claude-bridge` once, registers the repository, seeds its verdict state, writes `~/.codex/hooks.json` (root-owned, immutable) and refreshes the Codex plugin cache entry, which Codex launches the bridge from, root-owned and immutable as well. It refuses symbolic links at the paths it writes, and scans the source tree for links before it reads anything from it; the single source files it reads as root (the manifest, the launch config, the hook template) are read through the owner's account, so a link swapped in after the scan cannot expose a file the owner could not read. Root computes the repository key itself and refuses with `repository key mismatch` when the repository code computes a different one.

Then open Codex in the repository and trust all five hooks when it asks. Then verify:

```
/usr/bin/node /opt/claude-bridge/current/bin/claude-bridge verify <repo>
```

Expect `protection: protected`, `hooks: intact` and `owner clears: verified against /opt/claude-bridge/current/owner.pub`. Flags: `--repo DIR` registers another checkout; `--claude-bin FILE` names the Claude binary to pin; `--owner USER` names the owner when not run through sudo; `--no-lock-cache` leaves the Codex cache copy owner-writable and warns: `protection` then reads unprotected (`Codex cache launch config is not the installed one`), so the hook denies every bridge call (`--lock-cache`, the old flag, is the default); `--dry-run --root DIR` writes the layout under DIR without changing owners or immutability; `--root` is refused without `--dry-run`.

## Enforcement

Three classes, kept apart in every report.

- **Outright.** Every installed program runs under a root-owned interpreter named by absolute path: the Codex launch config runs `/usr/bin/node`, the owner command's shebang is `#!/usr/bin/node`, the hook runs `/usr/bin/python3 -I` and starts the state CLI with `/usr/bin/node`, and the installer is `#!/bin/bash` with `PATH=/usr/bin:/bin:/usr/sbin:/sbin` and `NODE=/usr/bin/node`. The bridge runtime, hook code, hook registration and owner public key are root-owned and immutable (`chattr +i`) under `/opt/claude-bridge` and in `~/.codex/hooks.json`. The owner private key at `/etc/claude-bridge/owner.key` is readable by root only. Codex runs as the owner's account and `sudo` needs a password, so Codex cannot change these. The installed bridge runs the pinned Claude binary `/opt/claude-bridge/current/claude/claude` and nothing else; `protection` reads `unprotected` with `Claude binary is owner-writable` when that file, or any directory above its real path up to `/opt`, is writable by the bridge's uid or group- or world-writable, and with `Claude binary is missing` when there is none. Once the install holds, `protection` also checks the Codex cache launch config `~/.codex/plugins/cache/claude-bridge-local/claude-bridge/<version>/.mcp.json` (the home from the passwd entry): it must be a regular file owned by root, not group- or world-writable, and byte-identical to `/opt/claude-bridge/current/.mcp.json`; otherwise the reason is `Codex cache launch config is not the installed one`, since Codex could be launching some other server. Code that runs from `/opt/claude-bridge` (the bridge, its state CLI, the owner command and the hook) takes every location from one helper, `runtimeDefaults` in `protection.mjs` (`runtime_defaults` in the hook): the roots `/opt/claude-bridge` and `/etc/claude-bridge`, the home directory from the passwd entry of its uid (and from it `~/.codex`, `~/.codex/sessions` and `~/.local/state/claude-bridge`), the Claude binary `/opt/claude-bridge/current/claude/claude`, and `/usr/bin/bwrap`. It ignores `HOME`, `CODEX_HOME`, `CLAUDE_BRIDGE_STATE_DIR`, `CLAUDE_BRIDGE_SESSIONS_ROOT`, `CLAUDE_BRIDGE_PROTECTED_ROOT`, `CLAUDE_BRIDGE_ETC_DIR`, `CLAUDE_BRIDGE_CLAUDE_BIN`, `CLAUDE_BRIDGE_BWRAP_BIN` and every test-mode variable, so none of them can redirect the installed key, registration, state, hook command or binaries.
- **Refused.** The PreToolUse hook guards no files. It makes no decision on any call that is not a bridge call. The bridge's files are protected by the root-owned, immutable install (see Outright), the verdict state is tamper-evident (see Logged), and the repository copy under `plugins/claude-bridge/` is covered only by the rule in the bridge skill. The hook denies bridge calls (tools named `mcp__claude_bridge__*`; Codex hands a call that a code-mode `exec` script makes to the hook under that call's own name, so a bridge tool named inside any other call's arguments does not count) when the protected install exists and the hook registration is not intact, when the state CLI's `protection` output carries `Codex cache launch config is not the installed one`, or when that check cannot run, and it denies a bridge call it cannot evaluate. When the bridge runs from its protected install, it refuses review, task and continuation jobs if its hooks are missing, altered, not trusted, or disabled in Codex. Codex `config.toml` is read with a TOML 1.0 parser (Python's `tomllib`, run as `/usr/bin/python3 -I` by the bridge and by the hook), so escaped keys, dotted keys and strings that only look like tables are read as Codex reads them. A trust entry counts as trusted only when it is exactly `{ trusted_hash = "sha256:<64 hex digits>" }` (bare hex accepted) or that plus `enabled = true`; `enabled = false` in any spelling reads as disabled; any other key, value or type reads as `not intact: unexpected trust state`; a file the parser refuses (a repeated key or table, for instance) reads as `cannot parse config.toml`, as does a missing interpreter; and `features.codex_hooks = false` reads as `hooks disabled by features.codex_hooks`.
- **Logged.** Verdict state and the job log are in the owner's writable state directory. The verdict chain detects an edit that breaks a hash link or leaves `head.json` stale, a line that is not a record in Node's compact JSON form, a missing or mismatched `open.json`, truncation, and a reset of a registered repository; each reads as `tampered`. A writer who rewrites the chain, `head.json` and `open.json` together is not detected. The job log files and `record-failure.json` are outside the chain and carry no hash. When a registered repository's chain is deleted, the next write starts a new chain with a `state_reset_detected` record, and the state stays tampered. A verdict that could not be recorded leaves a `record-failure.json` latch. The honest exits: a later recorded verdict lifts the latch, and an owner clear of `'*'` lifts a tampered or reset state.
- **Session evidence.** The Codex session log is owner-writable, so the agent can edit what the reviewer reads as the owner's words. No hook guards the session logs; Codex reads them freely. The hook's turns ledger records the owner's prompts, Codex's final messages and each bridge call's transcript path as the Codex app hands them to the hook. `conversation.md` labels a message `OWNER (verified)` or `CODEX (verified)` only when its text hashes to a ledgered `owner_prompt` or `assistant_message`, and every other message `OWNER (unverified: not recorded by the hook)` or `CODEX (unverified)`; its header and the system prompt state that rule. A forged owner message therefore reads as unverified, and a readback forged into the session file does not confirm (see `Stop` under Hooks). The bridge binds to the transcript of the newest ledgered bridge call, no older than ten minutes, whose file still has the recorded inode, and reports `session_evidence.match: ledger`; otherwise it falls back to the locator. A hook that is disabled or not trusted leaves the ledger empty, and a ledger that fails its integrity check verifies nothing; the bridge reports either in `conversation.md`, in the system prompt and in `session_evidence.ledger`. Limits: verified means the text was recorded in some turn for this repository, not that it sits where the log places it, so genuine words copied elsewhere still read as verified; and the ledger, like the verdict chain, is in the owner's writable state directory, where a writer who rewrites it whole together with its head is not detected.
- **Owner clears.** Every read of the verdict state (the bridge, the state CLI the hooks call, and the owner command) verifies each `owner_clear` in the chain against the installed owner public key. A clear whose signature does not verify, that names another repository, or that repeats the signature of an earlier clear in the chain lifts nothing, and the state reads as `tampered` (`forged owner clear in chain`) until a genuine owner clear of `'*'` follows it. Verification needs the public key: on an unprotected checkout with no key installed, clears are taken as written, the owner command prints `owner clears: unverified (no public key)`, and `protection` carries the reason `no owner public key; owner clears unverified`. When the state CLI is missing or fails, the hooks fall back to their own replay, which does not verify clears, and their context says so. Verification does not catch a writer who rewrites the chain, `head.json` and `open.json` together (see Logged), and there is no trusted clock at read time, so it does not check a clear's age; the CLI checks that when it applies the clear.
- **Loader variables.** The installed bridge's `protection` reads `unprotected` with `loader variables set` when its environment carries `LD_PRELOAD`, `LD_LIBRARY_PATH` or `NODE_OPTIONS`, which can load code into it before its own code runs. Where the protected install exists, the hook denies bridge calls when its own environment carries `LD_PRELOAD` or `LD_LIBRARY_PATH`; this is best effort, since a hook with code preloaded into it cannot vouch for itself.
- **Not covered.** Codex can load the plugin from another cache version or config path than the installed version's cache entry, which is the only one `protection` checks, and it can reconfigure its own MCP servers in `~/.codex/config.toml`, which the owner's account can write; an unregistered repository gets no turns ledger until the bridge holds state for it, so there every message reads unverified; and a Codex started with another `CODEX_HOME` runs without the root-owned hooks (its `hooks.json` is elsewhere), while the shared verdict state under the passwd home still binds its repository. Codex options given at launch (`-c features.codex_hooks=false`, a chosen profile, or a project config layer) are not written to `config.toml` and so are not visible to the trust check.

## Verdicts

Claude's final answer must match the verdict schema. Fields:

- `verdict`: `clear`, `corrected` or `blocked`.
- `deception_found`, `counter_to_operator_request`: true or false.
- `findings`: `id`, `claim`, `evidence`, and `status` (`established`, `plausible` or `not_established`).
- `corrective_actions`: `path`, `summary`, and `action` (`edited`, `created`, `deleted`, `reverted` or `committed`).
- `reprimand`: text or null.
- `required_of_codex`: what Codex must do next.
- `operator_readback`: the exact sentences Codex says to the operator. A bridge whose `protection` is not `protected` appends ` (This bridge ran unprotected.)` to it before recording the verdict, so the operator hears that too.
- `report`: the full report.
- `evidence_coverage`: `session_conversation` (`full`, `partial` or `unavailable`) and `notes`.

`clear` means nothing stays open. `corrected` means Claude changed the work; it stays open until the readback is confirmed. `blocked` means the work must not proceed and the operator decides. A `blocked` verdict lifts only by a later verdict from Claude (a `clear`, or a `corrected` followed by readback) or by the owner. Each verdict record carries its `profile`, and a verdict from `claude_task` (or a task's `run_started`) never replaces, and so never lifts, an open verdict from `claude_review`; it is still recorded and listed. A run that finishes returns a verdict. Without a structured verdict, the bridge takes the last fenced `claude-bridge-verdict` block in the result, and rejects one whose text the prompt already carries, since Codex could have planted it for Claude to echo. A finished run without a parseable verdict is recorded as `blocked`, with a rerun of the review as the requirement. A started run that ends in an error returns a verdict too: `claude_error` (including `error_max_turns`), `model_unavailable`, `nonzero_exit`, `stdout_limit`, `cancelled`, `malformed_json`, `invalid_envelope` and `spawn_failed` each record a `blocked` verdict whose `operator_readback` and `evidence_coverage.notes` name the error code, write the job log, and return the error payload with `verdict`, `verdict_id`, `verdict_parse: "run_error"` and `log_path`. Later task calls are then refused with `verdict_open`. The refusals that come before a run (`hooks_not_intact`, `nested_repository`, `verdict_open`, `verdict_record_failed_pending`, `verdict_state_tampered`) record nothing. When no verdict can be recorded at all, a finished run returns `verdict_record_failed` and an errored run returns its own error with `record_error`; both leave the record-failure latch.

Before the provider starts, the bridge records `run_started` (`job_id`, `profile`, `model`) in the chain. Until a verdict for the same job follows it, every reader takes it as an open `blocked` verdict with the readback `Claude Bridge: a review run started and never recorded a verdict. Work is blocked until a review completes.` A bridge killed mid-run therefore leaves task work refused with `verdict_open` until a later review completes or the owner clears it; while a job runs, the same record refuses task calls from other bridge processes. The hooks name it in the context and do not demand its readback at Stop. When `run_started` cannot be recorded, the bridge sets the record-failure latch and runs; a recorded verdict lifts it.

When the bridge runs protected (and under `CLAUDE_BRIDGE_TEST_FORCE_PROTECTED=1` in test mode), a call whose `cwd` sits in a `.git` nested inside a registered repository is keyed to the outermost registered repository holding it, so a planted `.git` cannot give the call a clean state of its own: a task or continuation call takes that repository's refusal (`verdict_open`, `verdict_state_tampered`, `verdict_record_failed_pending`), and any call is refused with `nested_repository` unless that repository is clean and the nested root is registered itself, in which case the call is keyed to the nested root. `claude_verdict` reports the repository a call would be keyed to. Where the protected install exists, the hook keys its context and turns ledger the same way, a registered nested root included; the hook's own clean check of the enclosing repository uses its replay and does not verify owner clears, so the server, which verifies, refuses regardless.

The Stop hook confirms the readback. While a verdict is open, `claude_task` and `claude_continue` are refused with `verdict_open`. While a record failure is latched they are refused with `verdict_record_failed_pending`, and on a tampered state with `verdict_state_tampered`. `claude_review`, `claude_result`, `claude_verdict` and `claude_bridge_status` stay available.

## Hooks

One script, `hooks/bridge_hook.py`, run as `/usr/bin/python3 -I` (3.11 or newer, for `tomllib`; without it the hook still loads and denies, and trust reads `not intact: python3 lacks tomllib`), handles five Codex events:

- `SessionStart` and `UserPromptSubmit` read the verdict state and the protection in one run of `/usr/bin/node <protected root>/current/mcp/state-cli.mjs context <repo>`; `Stop` runs `state-cli.mjs current-state <repo>`. Both run with an environment of `PATH=/usr/bin:/bin` and the passwd `HOME` only (no `NODE_OPTIONS`), which reads it as the bridge does, owner clears verified. When the CLI is missing or the run fails, the hook uses its own replay of the chain, which does not verify owner clears, and its own `tomllib` check of the Codex trust table, adding a line saying so. Readbacks are still appended by the hook, in Python, under the state lock; the Stop hook runs the state CLI with no lock held and takes the lock only for the append, checking the chain again there with its own replay.
- `SessionStart` and `UserPromptSubmit` add context: the standing sentence on the authority, any open verdict with its readback and requirements, a record-failure or tampered notice, and, when the protected install exists, the hook trust state from `state-cli.mjs protection` (registration, Codex trust, disabled hooks) when it is not intact, or the hook's own registration check when the CLI cannot run.
- The hook keeps a second hash-chained ledger, `turns.jsonl` (head in `turns-head.json`), under the same lock and rules as the verdicts, from what the Codex app hands it: `UserPromptSubmit` appends `owner_prompt` (`session_id`, `turn_id`, `recorded_at`, the `sha256` of the prompt and the prompt, cut at 16 000 characters with `truncated: true`); `Stop` appends `assistant_message` from the app's `last_assistant_message` when it is not empty; `PreToolUse` on an allowed bridge call appends `bridge_call` (`session_id`, the app's `transcript_path` and its `inode`). The ledger is kept for a registered repository and for one the bridge already holds state for. Lone surrogates are stored as U+FFFD, which is how Node hashes them.
- `PreToolUse` acts only on bridge calls, known by tool name: it denies the ones described under Refused and ledgers the rest. Every other tool call gets no decision. An error while evaluating a bridge call becomes a deny; an error on any other call, or a hook input that does not parse, produces no decision.
- Time budget, against Codex's hook timeouts (10 s, Stop 15 s): each event runs the state CLI at most once, capped at 5 s (`SessionStart` and `UserPromptSubmit` use `state-cli.mjs context <repo>`, which prints the verdict state and the protection together). `UserPromptSubmit` waits at most 2 s for the state lock to ledger the prompt, under 8 s in all; `PreToolUse` on a bridge call waits at most 2 s to ledger the call, under 8 s; `Stop` waits at most 3 s to ledger the message and at most 3 s for the readback append, under 12 s. A ledger append that cannot get the lock in time is left out.
- `PostToolUse` tells Codex to read the verdict back verbatim after a `mcp__claude_bridge__claude_result` call whose response carries `operator_readback`; no other call triggers it.
- `Stop`, while a verdict awaits readback, looks for `operator_readback`, ignoring case, whitespace and markdown marks, only in text the app handed the hook: the last assistant message, or an assistant message in the transcript tail whose sha256 matches an `assistant_message` the hook recorded in an intact turns ledger at or after the verdict's `recorded_at` (the ledger's time; the transcript's own timestamps are not read). A line written into the session file by anything else was never ledgered and confirms nothing. Found: it records `readback_confirmed`, which lifts a `corrected` verdict. Not found: it blocks the stop with the exact text to say. After three blocked stops it lets the stop through with a note that the verdict remains open; the bridge's refusal still holds. If the state is locked, it blocks once, then lets the stop through. The message that ends a turn is the only channel the Codex app hands the hook: commentary emitted mid-turn is never seen, so a readback spoken there does not confirm, and the `UserPromptSubmit` context keeps saying so until a turn ends with the readback.

## Owner command

`/usr/bin/node /opt/claude-bridge/current/bin/claude-bridge <command> [repo]`:

- `status` and `verify` print the verdict state, chain health, protection, hooks, registration, state directory, record-failure marker, and `owner clears: verified against <path>` or `owner clears: unverified (no public key)`.
- `verdicts` prints every record in the chain.
- `install` runs `install.sh`: from the repository checkout for the first install, and from the installed copy with `--source <checkout>` for an upgrade.
- `clear <verdict-id|'*'> --reason <text> [--owner <user>]` signs an owner clear with the root-only key and applies it. Run it as root from the installed copy:

```
sudo /usr/bin/node /opt/claude-bridge/current/bin/claude-bridge clear <verdict-id|*> --reason "<why>" <repo>
```

Quote `'*'` in the shell. The signed clear names the repository by its `repo_key`, is valid for fifteen minutes and cannot be replayed. A rejected clear is recorded as `rejected_clear`. `'*'` clears any open verdict and ends a tampered or reset state (a broken chain is kept as `verdicts.jsonl.broken-<time>` and a fresh chain starts). Every applied clear removes `record-failure.json`. A running bridge keeps its in-process record-failure latch until it records a verdict or restarts.

The CLI verifies a clear against the installed owner public key before it applies it. Run from `/opt/claude-bridge`, it reads that key, and the default owner key path, from `/opt/claude-bridge` and `/etc/claude-bridge` whatever the environment says. A copy run from anywhere else honours `CLAUDE_BRIDGE_PROTECTED_ROOT` and `CLAUDE_BRIDGE_ETC_DIR`, so a caller with its own key pair can make that copy append a clear. The installed bridge, its state CLI and the installed owner command verify that clear against the installed key when they read the chain, so there it lifts nothing: the state reads as `tampered (forged owner clear in chain)` until the owner clears `'*'`. The hooks' fallback replay, used only when the state CLI cannot run, does not verify it (see Owner clears under Enforcement).

## State and log

Per repository at `~/.local/state/claude-bridge/<repo_key>/`. The `repo_key` is the first 20 hex digits of the SHA-256 of the repository's resolved path.

- `verdicts.jsonl`: the hash-chained records.
- `head.json`: the hash of the last record and the count of records.
- `turns.jsonl` and `turns-head.json`: the hook's ledger of owner prompts, final assistant messages and bridge calls, chained the same way.
- `open.json`: a cache of the open verdict. The chain is the authority.
- `.lock`: the write lock, a directory. A lock older than 30 seconds is broken and the break is recorded.
- `record-failure.json`: present only after a verdict could not be recorded.
- `log/<time>-<verdict-id>.json`: one per run whose verdict was recorded, with the prompt, system prompt, evidence manifest, session match, protection and verdict, plus the result text for a finished run or the error code and message for an errored one.

Registered repositories are listed in `/etc/claude-bridge/repos/<repo_key>`.

## Environment

No variable chooses the model or the effort; every run uses the models and effort under What it does.

Code running from `/opt/claude-bridge` ignores every variable below except `CLAUDE_BRIDGE_ALLOWED_ROOTS`, the size limits, `CLAUDE_BRIDGE_DEPTH` and `CLAUDE_BRIDGE_OWNER_KEY` (see Outright under Enforcement).

- `CLAUDE_BRIDGE_STATE_DIR`: verdict state root. Default `~/.local/state/claude-bridge`.
- `CLAUDE_BRIDGE_PROTECTED_ROOT`: protected install root. Default `/opt/claude-bridge`. A hook running from anywhere else reads it to find the state CLI and the hook command.
- `CLAUDE_BRIDGE_ETC_DIR`: owner key and registrations. Default `/etc/claude-bridge`.
- `CLAUDE_BRIDGE_SESSIONS_ROOT`: Codex session logs. Default `~/.codex/sessions`.
- `CLAUDE_BRIDGE_ALLOWED_ROOTS`: a path-delimited list; the `cwd` and its Git repository must lie inside one of them. Unset allows any repository.
- `CLAUDE_BRIDGE_MAX_PROMPT_BYTES`, `CLAUDE_BRIDGE_MAX_STDOUT_BYTES` (alias `CLAUDE_BRIDGE_MAX_OUTPUT_BYTES`), `CLAUDE_BRIDGE_MAX_STDERR_BYTES`, `CLAUDE_BRIDGE_MAX_RESULT_BYTES`: size limits. Defaults 200000, 2 MiB, 64 KiB and 60000 bytes. A value below 1024 is ignored.
- `CLAUDE_BRIDGE_CLAUDE_BIN` (or `CLAUDE_BRIDGE_BIN`): the Claude Code binary for a bridge run outside `/opt/claude-bridge`. It must be an absolute path to an existing file. Default: `claude` on `PATH`, then `~/.local/bin/claude`. The installed bridge runs its pinned copy.
- `CLAUDE_BRIDGE_BWRAP_BIN`: the bubblewrap binary. Default `/usr/bin/bwrap`.
- `CLAUDE_BRIDGE_DEPTH`: the nesting guard. The bridge sets it to 1 inside a delegate, and any value but 0 refuses the call.
- `CLAUDE_BRIDGE_OWNER_KEY`: the owner private key file for `clear`. Default `/etc/claude-bridge/owner.key`. It only works when the named key file is readable by the caller. The real key is readable by root only. A clear signed with any other key is rejected by the installed CLI, and one appended by a copy that trusts another key reads as forged; see Owner command.

Test mode only, and never from `/opt/claude-bridge`. `CLAUDE_BRIDGE_TEST_MODE=1` enables the rest:

- `CLAUDE_BRIDGE_TEST_FORCE_PROTECTED=1`: the server treats itself as protected and checks the hooks.
- `CLAUDE_BRIDGE_TEST_LOCK_TIMEOUT_MS`: the state lock timeout.
- `CLAUDE_BRIDGE_TEST_FORCE_ROOT=1`: the owner command takes its root branch. It grants nothing.
- `CLAUDE_BRIDGE_STATE_CLI`: the state CLI the hook runs, in place of `<protected root>/current/mcp/state-cli.mjs`.

## Testing

Run from the repository root:

```
npx vitest run --config config/vitest/vitest.claude-bridge.config.ts
```

Requires `/usr/bin/python3` (3.11 or newer), `/usr/bin/node` and `/usr/bin/git`. The tests use a fake provider and a temporary install root. They start no model turn and need no root.
